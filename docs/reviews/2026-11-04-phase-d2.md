## Coupled numerical evidence

All simulation workloads were bounded. The packaged coupled model was a 10 mm STEP block, 79 tetrahedra, 337 degrees of freedom and p=1. No large 3D solve was run.

| Check | Evidence |
|---|---|
| Coupled solve and DC propagation | Converged in 2 iterations at 50 Hz with tolerance `1e-4`; magnetic residual `2.341e-11`, displacement residual `1.798e-6`. The DC field had 528 H(div) coefficients and reloaded against the exact mesh and input fingerprint. |
| DC cache invalidation | A harmonic-only frequency change reused the matching DC field. Changing the DC input forced recomputation and changed the coupled response. |
| Genuine two-way coupling | In the 79-element/337-DOF isolation case, disabling mechanical feedback changed the EM result by `6.67e-15`; enabling two-way feedback changed the AC field by `1.087e-4`. Maxwell-stress loading produced a nonzero mechanical response. Rotating the DC field changed DC, AC and displacement responses. |
| Complex excitation behavior | Doubling excitation produced field and displacement scaling errors of `5.86e-15` and `9.12e-16`. A quadrature phase shift produced field and displacement phase errors of `5.05e-15` and `6.97e-16`. |
| Analytical mechanics check | A 12-element free-body harmonic model matched its inertial analytical displacement at 50 Hz and 100 Hz to the printed precision. |
| Manufactured coupled h/p refinement | The existing 3D manufactured-solution baseline converged at p=2 and p=4. At p=2, increasing the bounded mesh from 80 to 86 elements reduced relative H(curl) error `0.2248 → 0.1674`, curl-A error `0.2154 → 0.1488`, mechanical L2 error `0.1552 → 0.1400`, and mechanical H1 error `0.1856 → 0.1722`. At p=4 on 80 elements/5,127 DOFs, those errors were `0.0884`, `0.000888`, `0.000290`, and `0.000462`. These are bounded manufactured-problem results, not broad predictive-accuracy claims. |

The packaged app also completed a deliberately nonconverged 79-element run with a two-iteration cap and tolerance `1e-8`. Its job state is `nonconverged`, its scientific status is `nonconverged_diagnostic_data`, and the saved fields are described as diagnostic only. The DC field was reused. A fresh packaged process restored the coupled physics, 50 Hz frequency, 0.025 T DC background, 1,000,000 A/m² source, iteration limit, and tolerance.

### WebGPU capability and best available path

The probe ran inside the maximized packaged desktop app, on its loopback origin. It did not open the 2D field viewer or select a saved result.

- Chrome `156.0.8078.74`; Windows 10 build `19045`; origin reported as a secure context.
- `navigator.gpu` was present, but adapter requests returned no adapter for default/high-performance, low-power, compatibility mode, or forced-fallback requests. Device creation and the tiny offscreen render therefore could not run.
- Chrome CDP reported `ANGLE_D3D11`, `VirtualBox Graphics Adapter (WDDM)` driver `7.2.20.25154`, `supportsDx12=false`, `supportsVulkan=false`, and Direct3D 12 feature level “Not supported”. A Microsoft Basic Render Driver was also listed. WebGL2 was available.
- The actual 3D STEP geometry and 12-element surface/volume preview rendered in the app. That path uses the existing WebGL preview and does not require WebGPU.

This isolates the WebGPU failure to the graphics environment rather than an insecure origin or missing browser API. Chrome's published Windows WebGPU path requires Direct3D 12; its compatibility-mode announcement describes Windows Direct3D 11 as still being explored. VirtualBox documents Windows guest 3D acceleration as Direct3D 11.0/11.1, matching the diagnostic output. See [Chrome WebGPU troubleshooting](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips), [Chrome WebGPU platform support](https://developer.chrome.com/docs/web-platform/webgpu/overview), [Chrome compatibility-mode status](https://developer.chrome.com/blog/new-in-webgpu-146), and the [VirtualBox 7.2 guide](https://download.virtualbox.org/virtualbox/7.2.2/UserManual.pdf).

**Recommended way to make WebGPU work:** run MagMechSim on Windows hardware or a hypervisor/virtual GPU that exposes a compatible Direct3D 12 adapter (for example, a supported GPU-passthrough/GPU-PV configuration), then rerun the packaged adapter/device/render probe. Enabling VirtualBox 3D acceleration can support the working WebGL preview, but this VM's current VirtualBox adapter does not expose D3D12. An application flag cannot supply the missing API. No unsafe browser flags were added. Until the environment changes, the in-app WebGPU results renderer remains unverified on this VM. Keep a real 3D WebGL route for geometry previews; do not substitute a flat CPU field view.

If this VM must remain on its current D3D11-only adapter, the appropriate software alternative is a **genuine 3D WebGL field renderer** with contours/vectors and interactive camera controls, selected only after the runtime WebGPU adapter/device/render probe fails. WebGL2 is available here and already renders the 3D geometry/mesh preview, but field-rendering parity has not been implemented or verified. That would be a future results-rendering milestone, not a 2D field-viewer fallback and not part of D2. The two paths should be kept distinct: provide D3D12 to make WebGPU work; build a true 3D WebGL renderer if a supported D3D12 environment cannot be provided.
