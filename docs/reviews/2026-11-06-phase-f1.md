## Summary

Phase F1 makes focused improvements to the shared application shell, 3D tree labels, axisymmetric canvas lifecycle and geometry-preview dismissal. It retains a common top-level navigation model while leaving the axisymmetric sketch tools and 3D OCC controls specialised to their workflows.

The packaged application was inspected through genuine native mouse/keyboard input and full-desktop screenshots at 1920×1094, with the app maximized for normal workflow screenshots. Both workflows were exercised: recent-project geometry thumbnails, 3D STEP geometry/property navigation and CAD selection, context-sensitive menus, Model/Results switching, axisymmetric sketch selection, responsive canvas sizing, and the axisymmetric geometry-creation 3D preview with Escape dismissal.

The startup sequence now checks native pixels at launch size, maximizes only after that check passes, checks the full-size client, and dismisses the splash after the maximized native-paint signal. This works on repeated launches, but is not fully reliable: two of nine observed fresh packaged windows produced zero visible native pixels after the frontend mounted and timed out at the restored-size gate. Later launches passed. The failure cause is not established, and the startup issue should not be described as fixed.

## Architectural and UX decisions

- Keep `NGSolveGui` as the shared application shell for File/Edit/View/Model/Study/Results/Help, quick-access actions and Model/Results navigation. Reduce the shared menu/header heights modestly rather than replace the shell.
- Keep the axisymmetric sketch toolbar and 3D CAD toolbar distinct. Their geometry models and supported interactions differ; sharing them would create false parity and risk specialised tools.
- Keep model-tree and property-editor details in their existing workspace implementations. Improve specific discoverability points without introducing a new cross-workspace abstraction.
- Rebind the axisymmetric sketch resize observer to a stable canvas host so a remounted SVG does not lose viewport sizing updates.
- Close the axisymmetric 3D geometry preview on Escape before the key reaches the underlying sketch tool.
- In the native launcher, use an ordinary initial Chromium window, verify its rendered native surface, maximize it, verify again, and only then dismiss the splash. There is no fixed startup sleep. If the native-pixel gate fails, startup remains diagnosable rather than being reported as a successful launch.
- No numerical solver implementation, formulation, dependency, project format or separate Mike variant was changed.

### Fresh-launch evidence

Across nine fresh packaged windows observed during this verification, **seven passed** both native-pixel gates and **two timed out** at the restored-size first-frame gate with `visible_pixels=0` after the frontend-mounted signal. The failures occurred in consecutive initial packaged-test attempts; the later full runs passed. The public launcher smoke also passed its native gates. A failure screenshot captured the restored Chromium client white with the startup diagnostic visible. It is retained locally but omitted from the share ZIP because it also exposes unrelated desktop content; the included test JSON preserves the zero-pixel diagnostics and timing.

On the final full packaged run, splash-to-ready was **9.48 s** for the 3D launch and **8.67 s** for the axisymmetric launch; the maximized native-paint handoff took **0.22 s** and **0.30 s**. The launcher smoke reached its home state in **9.485 s**. The VM had already moved to an SSD. These timings are observations, not a controlled before/after comparison, and no portion of any improvement is attributed to the code without such a comparison.

The frontend was mounted in both failed cases, but the native client remained white through the 15-second pixel probe and bounded repaint requests. This confirms an intermittent native presentation failure in this environment; it does **not** establish whether the cause is Chromium, the VM display stack, driver behavior, focus/compositing or another interaction. The native-frame checks prevent a false success signal, but a seamless startup has not been demonstrated on every attempt. The residual issue warrants a focused follow-up before broader UI work if it is not accepted as an environment-specific risk.

## Limitations and remaining work

- The native first-frame race is intermittent and its root cause is unresolved. Do not claim startup reliability is fully fixed. Verify a focused, bounded renderer/window recovery before relying on it as closed.
- One full UI-test attempt timed out at the axisymmetric 3D preview check, then passed on immediate full-suite rerun. Keep the improved failure-state evidence and investigate if it recurs.
- The 3D viewport and axisymmetric geometry-creation preview were verified on this Windows VM only; no physical-GPU comparison was made.
- This milestone improves the shell and selected interaction seams. It does not establish complete parity between every 3D and axisymmetric property editor, assignment flow, toolbar or validation message. Those remain appropriate F2 review topics.
- No large 3D simulation or solver numerical benchmark was run. No numerical behavior was changed.
- The SSD move is an uncontrolled performance confounder.
