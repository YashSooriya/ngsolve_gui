# MagMechSim Phase F1.1: Native Startup Stabilization

**Date:** 6 November 2026  
**Status:** Complete for the tested Windows VM; ready for independent review  
**Scope:** Resolve the intermittent blank/delayed native first frame. No numerical solver or UI redesign work was included.

## Finding

The failure was in the packaged Windows application's native Chromium surface, not a frontend mount failure. The browser DOM and `#q-app` could be present while the actual window remained white or showed only an incomplete startup/loading view. A corrected packaged diagnostic inspected the actual ngapp root (`#q-app`; an earlier probe mistakenly queried `#app`). The native gate requires the app HWND to be foregrounded and captures its client area while excluding the branded splash.

Before the fix, a fresh packaged no-flag run had zero above-threshold native pixels in six full-desktop captures taken 0.15, 0.5, 1.5, 4, 8 and 12 seconds after the restored window appeared. The run then failed its native first-paint gate and recorded the real HWND bounds, foreground state, pixel count and one bounded repaint request. A later diagnostic screenshot after that failure contained the app's error dialog and an incomplete home/loading view; it is not evidence that the startup gate had passed. The earlier Phase F1 seven-of-nine outcome remains historical, pre-fix evidence.

A controlled comparison changed only Chromium's `CalculateNativeWinOcclusion` feature for the dedicated MagMechSim app window. The two flag-enabled comparison runs passed the restored and maximized native paint gates. Measured restored frame capture took 0.047–0.079 s and maximized frame capture took 0.125–0.172 s. This identifies Chromium native-window occlusion as the trigger on this VM. It does not establish that every graphics driver or Chromium build has the same failure.

## Implementation

- `coupled_solver/release/native_windows/desktop.py` adds `--disable-features=CalculateNativeWinOcclusion` only in the `PRODUCT_NAME == "MagMechSim"` Chromium app-window path. The existing native first-frame gate and splash handoff remain in place.
- The `MM-FEM`/Mike branch is explicitly covered by a test asserting that it does not inherit the flag. No Mike feature set was otherwise changed.
- The package build metadata lists the workaround. The packaged test diagnostics use the actual ngapp root and read back only the expected sanitized launch argument.
- No WebGPU/WebGL, rendering or numerical algorithm was changed. No fixed startup sleep or substitute 2D viewer was introduced.

## Limitations and risks

- Verification used the Windows 10 VM and its current Chromium/VirtualBox display path. A physical Windows GPU and alternate Chromium/driver versions were not tested.
- Disabling native occlusion may reduce Chromium's ability to avoid rendering when the dedicated app window is fully obscured or minimized. Measure background CPU/GPU use on supported hardware if it becomes material.
- The screenshot package includes fresh Phase F1.1 captures dated 6 November 2026, organized separately from the pre-fix white-frame diagnostic. It does not present the older Phase F1 screenshots as current evidence.
- No solver simulations or numerical benchmarks were run, because the change is confined to native app launching.
