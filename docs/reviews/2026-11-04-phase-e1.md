## What changed

The 3D Study editor now supports a single frequency, an explicit list, or an evenly spaced range. The project model validates these definitions, limits a sweep to 50 points and frequencies to `1e9 Hz`, and migrates existing schema-v1 projects to schema v2 with their single-frequency behavior preserved. EM-only, mechanics-only, and fully coupled 3D workflows use the existing solver execution path. Run metadata records per-frequency progress, outputs, execution state, scientific convergence state, and failure/cancellation details.

The frequency loop and run-state integration remain in the GUI adapter. Existing NGSolve electromagnetic and mechanical formulations, solver dependencies, and numerical algorithms were not changed. The only new numerical-regression change in the GUI repository adds an independent same-mesh EM sweep-versus-single-frequency field comparison.

| Workflow | Phase E1 support and verification |
|---|---|
| 3D harmonic EM-only | Single, explicit-point and range frequency definitions; per-point outputs and status. Same-mesh fields agree with independent single-frequency solves. |
| 3D harmonic mechanics-only | Sweep propagation and per-point results. Same-mesh comparisons agree with independent single-frequency solves to `<1e-8` relative L2. |
| 3D fully coupled | Per-frequency DC compatibility/reuse and convergence reporting. A packaged 79-element model converged at 50 and 60 Hz; a strict rerun remained execution-complete while correctly marked scientifically nonconverged. |
| Axisymmetric geometry creation | Existing editable sketch workflow remains. Its 3D preview was tested in the packaged desktop and renders through interactive Plotly WebGL, without a WebGPU adapter. No axisymmetric solver formulation was changed. |

## Numerical verification

- For the exact same mesh and model, EM sweep versus single-frequency `gfBAC` relative L2 differences were `7.332e-15` at 50 Hz and `7.507e-15` at 100 Hz. The test also compares the serialized mesh bytes before comparing fields.
- Mechanics sweep versus separate single-frequency fields agreed below `1e-8` relative L2 at both checked frequencies.
- Coupled 50/60 Hz sweep outputs agreed with separate single-frequency solutions within the configured fixed-point tolerance (`1e-4`). The packaged, bounded 79-element, p=1 model converged at both points in two iterations. Its exact DC reload used 528 H(div) coefficients and matched the required mesh SHA-256 and input fingerprint.
- A stricter packaged rerun capped at two iterations with tolerance `1e-8` produced `execution_status=complete` but `scientific_status=nonconverged` at both points. The run history presented it as nonconverged diagnostic data rather than a successful solution.
- Existing manufactured-solution tests were preserved and passed. These bounded comparisons verify implementation consistency; they do not establish broad predictive accuracy for arbitrary engineering models.

It was launched three times from isolated test profiles. The main window was maximized on a `1920×1094` desktop for every capture. The test exercised the 3D project, geometry/mesh preview, study configuration, frequency-list editing, native Run activation, converged and nonconverged study runs, result/run-history status, save/reopen, axisymmetric geometry editing, the 3D geometry preview, native camera rotation, return to the sketch editor, and process cleanup.

The runner recorded 29 screenshot capture events and produced 28 distinct PNG files: `three-d-07a-file-menu.png` appears twice in the capture metadata because the same path was captured twice. The review ZIP includes every distinct image file.

The package's preview reported two 3D mesh traces, a live WebGL canvas, no renderer warning, and an actual camera change following a native mouse drag. This is a genuine 3D preview path, not the retired CPU-only 2D field viewer. The package check confirmed the viewer module is absent and there is no menu command for it.

Observed splash-to-maximized times were `8.692 s`, `7.084 s`, and `7.113 s`; the separate fresh-profile `Launch-Latest-MagMechSim.cmd` smoke reached the home workspace in `12.125 s`. The VM had been moved to an SSD before these measurements, so they are observations only and cannot be attributed to code or compared with earlier storage conditions as a controlled benchmark. All package-owned processes were gone after test cleanup.

### WebGPU and the required 3D fallback

The packaged app ran on a secure loopback origin and reported `navigator.gpu` present, but neither the high-performance nor compatibility WebGPU adapter request returned an adapter; no device could be created. WebGL2 was available through `ANGLE (VirtualBox Graphics Adapter (WDDM), Direct3D11)`. The axisymmetric geometry-creation preview therefore works using its existing interactive Plotly WebGL 3D renderer; it does not need WebGPU. The actual packaged test verified visible geometry and native camera rotation.

**Carry-forward requirement for the orchestrator:** never restore or use the retired CPU-only 2D field viewer. When WebGPU is unavailable, any user-facing geometry/mesh preview must remain a genuine interactive 3D renderer; this packaged application already demonstrates that path with Plotly WebGL. For any future WebGPU-dependent results view, either provide a supported adapter-capable graphics environment or separately implement and verify a genuine 3D WebGL results renderer. Do not present a flat 2D field view as an equivalent fallback, and do not force experimental browser flags. Chrome documents its Windows WebGPU route around Direct3D 12; the current VirtualBox guest reports Direct3D 11. See [Chrome WebGPU overview](https://developer.chrome.com/docs/web-platform/webgpu/overview) and the [VirtualBox 7.2.20 manual](https://download.virtualbox.org/virtualbox/7.2.20/UserManual.pdf).

WebGPU-based result rendering was not exercised in Phase E1 and is not claimed as working in this VM. The tested preview is the axisymmetric geometry-creation stage, not results post-processing.

## Limitations and recommendation

- Numerical comparisons use small bounded models; no large 3D simulation was run.
- Native package cancellation and forced solver-failure behavior were not exercised; the browser lifecycle checks use a fake child process.
- WebGPU results rendering remains unverified on the VirtualBox D3D11-only guest. The geometry-creation 3D preview is verified through WebGL and remains interactive without WebGPU.
- Startup timing is confounded by the SSD migration and is not a controlled before/after performance benchmark.

**Recommendation:** ready for independent review of Phase E1 for the tested scope. Do not automatically start Phase E2. After approval, the roadmap's next candidate is ROM study management, while keeping the CPU-only 2D viewer retired and preserving genuine 3D rendering paths.
