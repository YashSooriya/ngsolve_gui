## Summary

Phase E3 adds three supported numerical controls to the 3D study workflow: independent curved mesh geometry order, Rayleigh damping coefficients, and coupled Anderson depth/relaxation. Validation, solver propagation, project persistence, run provenance and invalidation were checked. The axisymmetric editor and its specialized mesh controls remain intact. The completed work introduces no new dependencies and does not change the FEM formulation or numerical algorithms.

The existing ROM builds its mechanical modal basis once per study run and reuses it across that run's frequency points. On the bounded 378-element model used here, basis construction took 37–49 ms. The results do not establish a sufficiently large repeated-run payoff to justify a persisted ROM artifact. Keep the existing per-run lifecycle; revisit cross-run reuse only if larger repeated-model workloads show material setup cost.

## Capability and configuration assessment

| Capability | Current implementation | Phase E3 decision |
|---|---|---|
| FE approximation order | 3D global p=1–4; axisymmetric global p=1–6. | Already exposed and persisted; retained. These select formulation spaces and are not local p-adaptivity. |
| Curved geometry approximation | Axisymmetric has its own curve-order control. The 3D runner previously tied mesh curve order to p. | 3D now supports “Match FE order” for legacy behavior or independent geometry order 1–6. It is validated, saved and recorded separately from p. |
| h refinement / mesh size | 3D supports per-domain target element size. Axisymmetric exposes its mesh sizing controls. | Existing controls retained. There is no automatic adaptive h-refinement loop. |
| p/hp refinement | 3D has no user-selected local p distribution; its GUI solver path initializes hp-layer settings empty/disabled. Axisymmetric supports specialist hp boundary layers. | Preserve the difference; do not imply 3D hp adaptivity. Existing axisymmetric hp settings are unchanged. |
| Mesh quality/algorithm | Target element sizes and meshing are supported; the application uses its configured mesher defaults. | No quality metric/optimization selector is available end-to-end, so none was added. |
| FE spaces and formulation options | NGSolve spaces are selected by the chosen physics formulation and its adapter. | No arbitrary space selector: the application does not expose unsupported space/formulation combinations. |
| Linear solvers and preconditioners | The packaged 3D study adapter selects direct sparse solve settings. Lower-level iterative/BDDC branches exist in solver code but are not a verified selectable full GUI path. Axisymmetric solver controls remain formulation-specific. | Do not expose CG, preconditioner or linear residual settings as if users could select a verified end-to-end 3D alternative. Direct factorization has no iterative tolerance to tune. |
| Static condensation / quadrature | The 3D adapter fixes condensation by subsystem (`statCondEM=True`, `statCondMech=False`, and DC-dependent `statCond`) and fixes integration settings. Some low-level condensation combinations carry solver stability concerns. | Keep the tested policy fixed. A UI choice needs solver-specific equivalence, stability and performance evidence first. |
| Harmonic and coupled controls | E1 frequency modes/sweeps and D2 coupling tolerance/iteration limit are already exposed. | Retain them; add Anderson depth 0–100 (0 disables acceleration) and relaxation in `(0,1]`. Validation requires at least two iterations when acceleration is enabled. |
| Mechanical damping | Axisymmetric Rayleigh α/β are already propagated. The 3D solver assembles mass- and stiffness-proportional terms but its GUI adapter previously supplied zero for both. | Add 3D α (1/s) and β (s), only when mechanics is active, with finite nonnegative validation. |
| ROM controls | E2 exposes mechanical ROM, SciPy/PINVIT, mode count and relevant PINVIT/enrichment settings in supported workflows. | Preserve all E2 behavior. No offline electromagnetic, transient or reusable-basis controls were added. |
| CPU/threading | No supported per-study thread control is wired through the packaged 3D workflow. | No UI placeholder. Use application/runtime defaults. |

The 3D GUI stores `mesh_geometry_order="match_finite_element"` by default, so older `.mmfem3d` projects retain their previous `mesh_curve_order=p` behavior. Explicit geometry order is capped at 6. A changed geometry order changes the generated mesh and the DC coefficient space; the DC fingerprint is now schema version 2 and includes that order. Rayleigh damping and Anderson settings do not invalidate an unrelated DC result. The runner has no generic assembled-system cache: it builds a mesh for a new study run or reloads the exact mesh packaged with a valid DC cache, and assembles the requested operators. The mechanical modal basis remains in-memory for that run only.

## Numerical verification

The real NGSolve test `test_mesh_geometry_order_and_rayleigh_damping_reach_a_real_3d_solve` compared otherwise identical curved-sphere models and a supported 10 mm mechanical block:

| Check | Result |
|---|---:|
| Sphere volume, geometry order 1 | `4.74507572e-7 m³` |
| Sphere volume, geometry order 4 | `5.23601691e-7 m³` |
| Analytic 5 mm-radius sphere volume | `5.23598776e-7 m³` |
| Geometry-order-4 relative volume error | approximately `0.00056%` |
| Mechanical displacement norm with β=0.001 s / undamped norm, 50 Hz | `0.954028` |

The damped displacement remained finite and complex. This demonstrates mesh-geometry propagation and the expected response direction for the tested load/model; it is not a general accuracy claim for damping calibration.

The bounded coupled regression used a 79-element STEP model, a computed DC field, nondefault Anderson depth 2 and relaxation 0.75, and the existing block Gauss–Seidel solver. It converged in two iterations with residuals `2.341e-11` (magnetic) and `3.622e-6` (mechanical). The test asserts that the settings returned by the solver match project/run metadata, that the DC result is reused for a harmonic-only change, and that changing the DC source changes the displacement. A separate capped-iteration branch remains correctly identified as nonconverged. At 50 and 60 Hz, sweep-versus-separate-solve relative L2 differences were between `1.335e-6` and `1.562e-5` for the recorded electromagnetic and displacement fields.

## ROM performance and reuse recommendation

The repeatable resource measurement used a bounded 378-tetrahedron mesh, 130 vertices, p=1, 315 free mechanical DOFs, six modes and frequencies 50/100/150 Hz:

| Measurement | Full order | ROM first run | ROM repeat run |
|---|---:|---:|---:|
| Solver wall time | 0.867 s | 0.338 s | 0.581 s |
| Basis construction | — | 0.049 s | 0.037 s |
| Online harmonic solve | — | 0.142 s | included in total |
| Whole-process sampled peak RSS | 176.9 MB | 183.0 MB | 183.1 MB |

The dense six-mode basis estimate alone was 15,120 bytes; RSS includes Python, NGSolve, SciPy and all other process allocations, so it is not basis memory. Six-mode relative displacement errors were `5.536%` at 50, 100 and 150 Hz. More modes may improve error, but the model-size evidence here does not establish a general ROM speedup or an accuracy-acceptable mode count.

At 315 free DOFs, basis construction is only 37–49 ms and repeat-run wall time varied substantially. This does not justify the implementation, fingerprinting, persistence, invalidation and validation burden of cross-run artifacts. The existing lifecycle already builds once per run and reuses that basis for every frequency in the sweep. **Recommendation: do not start a persistent-ROM milestone now.** Reconsider after a moderate-size repeated-study benchmark demonstrates material basis setup cost and reliable accuracy benefit. A future reuse fingerprint would need to match the assembled mechanical stiffness/mass operators and constrained subspace (including mesh, FE order, mechanical material assignment/properties and supports/springs). Changes to loads or frequencies may leave those operators unchanged but still need held-out accuracy checks; Rayleigh-damping changes have not been verified across persisted-basis reload. The current implementation creates no cross-run basis artifact and cannot become stale.

The full measurements are in `evidence/rom_resource_benchmark.json` in the review ZIP. Timings were collected on the SSD-migrated four-core Windows VM. There is no controlled comparison before versus after the SSD move or against another machine; these numbers are local observations, not portable performance guarantees.

## Remaining limitations and recommendation

- The known initial white Chromium frame remains; the test confirms actual workspace rendering after navigation, not a fix to first-frame painting.
- No user-selectable 3D iterative linear solver, preconditioner, adaptive h/p refinement, mesh-quality algorithm, thread count, or static-condensation policy was added. Those controls need verified supported solver paths and numerical comparisons before being presented to engineers.
- The 378-element ROM study is intentionally bounded and too small to establish the value of persistent bases. Do not infer larger-model scaling from its subsecond timings.
- Full-order comparisons are mathematical checks on the named test models, not predictive validation across all MagMechSim applications.
- Phase E3 changed only full MagMechSim GUI/solver integration. It did not alter the separate Mike variant, restore the retired CPU-only 2D viewer, or change the supported WebGPU-to-WebGL fallback.

The implementation is committed and pushed to the `testing` branches. The user-facing launcher points to the tested `0.2.8.dev305` package. The E3 review ZIP contains this report, the updated living roadmap, screenshots, test logs, run reports, build metadata and ROM benchmark. It omits the 1.7 GB runtime/executable; the package remains at the path above and its exact hash is recorded here and in `Build-info/build.json`.

**Recommended next milestone:** after independent acceptance, proceed to Phase F's incremental cross-workflow UX consistency. Keep the mature axisymmetric geometry and hp controls specialized. Defer persistent ROM until a representative repeated-study benchmark justifies it.
