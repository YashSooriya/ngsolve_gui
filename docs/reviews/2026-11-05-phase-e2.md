## Summary

Phase E2 connects MagMechSim's existing mechanical modal reduction to the Study and solver-settings workflow. It is a mechanical modal ROM, not a general electromagnetic or parametric ROM. The solver still assembles the full electromagnetic and DC systems; for eligible studies it reduces the mechanical harmonic block. Settings are saved with the project, passed into the existing NGSolve code, and recorded with run provenance and basis/solve timing.

No finite-element equations, numerical algorithms or solver dependencies were changed. The implementation reuses `red_matrix`, the existing SciPy/PINVIT eigensolvers, and the existing modal mechanics solve path. The GUI does not claim an offline model or a reusable basis file that does not exist.

## Supported capabilities

| Workflow | Availability | Scope and constraints |
|---|---|---|
| 3D harmonic mechanics-only | Full order or mechanical modal ROM | SciPy sparse eigensolve or PINVIT; mode count; PINVIT limits/tolerances; optional static load and boundary enrichment. |
| 3D fully coupled harmonic magneto-mechanics | Full order or mechanical modal ROM | The mechanical block is reduced. Harmonic electromagnetics, the DC background calculation/cache, and coupling iteration remain full order. Existing matching-DC checks still apply. |
| Axisymmetric harmonic EM + mechanics | Full order or mechanical modal ROM | The existing axisymmetric solver supports this configuration. Static enrichment is disabled because it is a 3D-only capability. |
| Axisymmetric mechanics-only | Full order | The existing axisymmetric ROM path requires harmonic EM to be active, so the GUI resets/disallows ROM and the solver adapter rejects an incompatible direct configuration. |
| Electromagnetic-only, DC-only, transient or electromagnetic ROM | Full order only / unsupported ROM | No electromagnetic or transient reduction method exists in the implemented ROM path; no corresponding controls are exposed. |

The project stores the solution method and normalized options. Supported settings include 1–500 requested modes, SciPy or PINVIT, PINVIT iteration and residual/eigenvalue tolerances, and 3D static enrichment. The actual number of modes and free/total mechanical DOFs are recorded because a requested basis size can be limited by the current finite-element space. PINVIT must converge before the GUI runner accepts the basis.

The basis is generated at run setup from the current assembled mechanical matrices and reused at each frequency in that solver sweep. It is not saved as a standalone offline model and is rebuilt for the next run. Therefore the current UI has no ROM-file status, stale-basis warning, training-frequency selector or cross-run cache. Changes to the model are incorporated by the next run's new assembly and basis build. This avoids silently applying a basis generated from different geometry, mesh, material or mechanical conditions.

## Implementation and architecture

- `src/ngsolve_gui/mechanical_rom.py` defines shared defaults, normalization and setting validation for the two frontends.
- `src/ngsolve_gui/three_d_workspace.py`, `src/ngsolve_gui/three_d_solver.py` and the 3D project schema expose modal mechanics only for supported harmonic mechanics/coupled studies and preserve settings in `.mmfem3d` projects.
- `src/ngsolve_gui/solve_workspace.py` and the axisymmetric model/editor expose the existing axisymmetric coupled-ROM configuration, gate it on harmonic EM plus mechanics, and keep 3D-only enrichment disabled.
- `coupled_solver/src/common/pre/red_matrix.py` remains the shared basis builder. `coupled_solver/main.py` builds the basis from the current operators. The 3D mechanical and coupled solvers consume that basis; electromagnetic operators remain unreduced.
- `coupled_solver/scripts/run_gui_3d_model.py` propagates project settings and records requested/actual modes, eigensolver, DOFs, static enrichment, PINVIT outcome and solver performance in the run manifest. The axisymmetric GUI runner records corresponding ROM provenance and diagnostics.
- Run history labels the method and mode count and keeps execution status distinct from coupled scientific convergence.

The separate Mike app was not modified. The retired CPU-only 2D field viewer remains absent. The accepted WebGPU capability check and automatic WebGL fallback remain unchanged.

## Numerical verification

All comparisons use the same geometry, mesh, materials, boundary conditions and excitation for their full-order and reduced runs. They are bounded regression cases, not broad predictive-accuracy claims.

| Case | Reduced basis | Relative difference from full order | Other evidence |
|---|---:|---:|---|
| 3D harmonic mechanics, 12 tetrahedra, 50 and 100 Hz | 6 modes | Displacement `5.869e-2` | Same error at each tested frequency for this linear case. |
| Same 3D mechanics case | 13 modes | Displacement `1.464e-2` | Error decreases at both frequencies; the automated test checks this monotonic improvement. |
| 3D coupled harmonic case, 79 tetrahedra, reused matching DC field | 6 modes | `gfAAC 1.294e-7`; `gfBAC 6.939e-6`; displacement `8.968e-3` | Coupling converged in 2 iterations. |
| Same coupled 3D case | 13 modes | `gfAAC 3.647e-8`; `gfBAC 8.596e-6`; displacement `2.937e-3` | Displacement error improves; both EM differences remain below the configured `1e-4` coupling tolerance. EM differences are near solver/fixed-point noise and are not asserted to improve monotonically. |
| Axisymmetric coupled harmonic case, 302 elements | 8 modes | Displacement `3.093e-1` | Coupling completed in 2 fixed-point iterations. |
| Same axisymmetric case | 24 / 40 modes | Displacement `5.576e-2` / `1.199e-2` | Error falls as the retained basis grows. |
| PINVIT eigenproblem | 4 modes in the small 3D elasticity reference | Eigenvalues agree with SciPy shift-invert to `rtol=1e-7` | PINVIT convergence and residual checks are required for acceptance. |

The 3D frequency-sweep regression compares each ROM frequency against a same-mesh full-order result. The coupled test separately reuses the same DC background for its full-order reference and ROM runs, checks the matching DC fingerprint, verifies convergence, and checks EM and displacement fields separately. The axisymmetric comparison is a coupled solver run, not just a configuration/manifest assertion.

## Performance observations

The small 12-tetrahedron 3D mechanics comparison measured full-order wall time `0.389 s`, six-mode ROM `0.386 s`, and thirteen-mode ROM `0.288 s`; basis setup was `0.014 s` and `0.013 s`. This is too small to establish a general speedup and shows the low-mode case can cost essentially the same as full order.

On the 79-tetrahedron coupled comparison with a reused DC field, one run measured `0.730 s` full order, `0.504 s` at six modes, and `0.524 s` at thirteen modes. Basis setup was `0.013–0.014 s`. This is encouraging for that bounded case but is a single short timing; it is not a performance guarantee. The packaged 3D GUI run used 6 of 15 free mechanical DOFs (27 total) and reported `0.021 s` basis setup, `0.078 s` online harmonic solve and `0.221 s` total solver wall time.

The 302-element axisymmetric test measured basis setup of `0.016/0.018/0.020 s` for 8/24/40 modes. Memory was not measured. Timings ran on the VM after it had been moved to an SSD; there is no controlled before/after storage comparison. Repeated larger workloads are needed before setting a break-even recommendation.

## Remaining limitations and recommended Phase E3

1. The current ROM is an online mechanical modal basis built afresh for each run. It does not offer offline training, disk persistence, parameterized model reduction, cross-run reuse or a stale-model workflow.
2. Electromagnetic reduction and transient ROM are not implemented. Coupled cases reduce mechanics only. Axisymmetric mechanics-only ROM remains unsupported by the current backend and is blocked.
3. Low-order bases can produce visible displacement error; increase mode count and validate against a full-order reference for the actual operating range. The examples here do not certify accuracy on other models or frequency ranges.
4. Short runtime measurements are noisy, and memory/break-even cost was not measured. Do not market the feature as always faster.
5. Post-processing visualization, WebGPU hardware-specific testing, WebGL feature limits and spare Results-viewport height remain on the existing roadmap and were not re-investigated here.

Recommended E3: first benchmark repeated multi-frequency studies on a representative but bounded model. If those workloads benefit from basis reuse, implement an explicit offline/reusable basis lifecycle with fingerprints covering geometry/mesh, mechanical material and supports, finite-element order/spaces, active physics and basis settings; add stale/incompatible recovery and held-out-frequency validation before exposing a reusable ROM file. Keep EM/DC full order unless a separate verified reduction method is developed. Do not begin E3 before independent review.
