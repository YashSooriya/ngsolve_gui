# LORENTZ Phase G2: Contextual Offline Documentation Search

**Status:** Complete for the tested scope; submitted for independent review  
**Date:** 7 November 2026  
**Package:** `0.2.8.dev338`  
**Scope:** Add contextual, offline documentation search to the shared application UI, correct two documentation capability descriptions, and verify the packaged Windows workflows. No solver behavior or project format changed.

## Summary

The shared app header now searches real sections from the version-matched Sphinx site shipped with LORENTZ. Results show a section title, page context and excerpt; selecting one opens the matching local heading. Search is available in both 3D and axisymmetric workspaces. Keyboard focus, arrow selection, Enter, Escape, and the no-match state were exercised using native input in the packaged app.

## Implementation and architectural decisions

- The documentation build parses the **generated Sphinx HTML**, extracting actual section titles, page titles, text and anchors. This keeps search content aligned with the documentation delivered to users, rather than maintaining a second hand-authored search corpus. The generated JSON is deterministic and version-tagged.
- The shared ngapp header owns the search control, so the same interaction is available across workspaces without duplicating UI. The index is loaded on first search use, validated against schema and app version, bounded in size/entry count, and cached for subsequent queries. Normal startup does not parse the corpus.
- Ranking boosts title and page-context matches, phrase matches and workflow-oriented user-guide content. Result count is capped at five; excerpts are chosen from indexed section text. Links are validated to remain inside the installed documentation root and against the target page's real anchors.
- Search controls and results use dedicated CSS classes for DOM discovery; ngapp's internal `id` is not assumed to become an HTML `id`. ARIA listbox/option state is initialized after result rows render, which fixed keyboard navigation for asynchronously created rows.
- The UI includes a visible empty state and falls back to Help → Documentation if the offline index is unavailable. No web search or external service is used.
- The G1 user guide was corrected in two places while adding the index: it distinguishes 3D single/list/range frequency inputs from axisymmetric expression lists, and accurately limits static load/boundary enrichment to the supported 3D mechanical ROM path.

### Real packaged desktop workflows

The packaged test ran on Windows 10 in a **maximized 1920×1094 desktop**. It opened the seeded 3D STEP project and axisymmetric geometry project, interacted with the actual header search, and used Help → Documentation. No simulation was started. For each workspace it verified five displayed results, visible excerpts, native typing, keyboard navigation to the expected result, opening the exact local Sphinx heading, version-matched Help landing page, Escape dismissal and an explicit no-match message. The 3D target was “CAD changes and assignment recovery”; the axisymmetric target was “Select a supported study.” Both documentation browser windows were maximized.

Input was sent using Win32 `SendInput`; screenshots used Pillow `ImageGrab` full-desktop captures; Playwright over isolated loopback CDP was used for read-only DOM/state checks. The test used an isolated browser profile and blocked external requests (Chrome host resolver mapped all names to not-found, proxy pointed at `127.0.0.1:9`, background networking disabled). The recorded documentation resource list was empty outside the local files. Test-owned application/browser processes were cleaned up after the run. The native report and full-resolution screenshots remain in the Phase G2 evidence directory.

The public `Launch-Latest-LORENTZ.cmd` now points to the tested dev338 package. A paired observation compared three fresh launches of accepted G1 `0.2.8.dev332` with three of G2 `0.2.8.dev338` on the same SSD-hosted VM using the same harness and fresh profiles:

| Package | Start-to-home values | Median |
|---|---|---:|
| G1 dev332 | 22.703, 11.265, 12.031 s | 12.031 s |
| G2 dev338 | 11.344, 11.531, 11.563 s | 11.531 s |

The G1 first-run outlier widened its range. These figures do **not** establish a code-caused startup improvement: Windows cache state and background load were not controlled, and the VM's SSD move is a confounder. The supported conclusion is that dev338 passed repeated startup checks and has comparable warmed start-to-home timing in this sample.

## Limitations and risks

- Search ranking was exercised with six representative engineering queries and two actual native workspace workflows, not an exhaustive synonym set or every section/configuration.
- The desktop test verifies the VM's packaged browser/renderer and local offline files; it does not add physical-GPU or other-machine verification.
- The frontend artifact was reused from G1 because G2 only changes the server-side UI and generated documentation index. Its packaged fingerprint matches the G1 source artifact.
- One harmless pytest plugin rewrite warning remains. No test failure was suppressed.
- No solver code or numerical algorithms were changed, and no numerical simulation was run in this documentation/search milestone.
