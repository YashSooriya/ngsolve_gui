## Outcome

Phase G1 refreshed the existing Sphinx site into version-matched offline Help for the Windows LORENTZ application. It leads with GUI workflows for engineers and keeps Python/API, benchmark and notebook material in a clearly identified advanced reference. It does not implement G2 search, alter the UI, change solver behavior or project formats, or run a simulation.

The packaged Help was opened from both 3D and axisymmetric workspaces in the maximized application. The 3D STEP viewport and axisymmetric sketch were visible at the full 1920×1094 desktop size. The docs landing page displayed `LORENTZ 0.2.8.dev332`; representative navigation and a benchmark with equations worked offline.

## Documentation coverage

The user guide now addresses:

- Windows launch, project creation/open/save/reopen and offline Help.
- Axisymmetric drawing, units, selection, snapping and supported geometry constraints.
- STEP/OCC geometry, bodies/faces, named selections and safe recovery after CAD changes.
- Materials, active physics compatibility, boundary conditions, sources and loads.
- Meshing, FE order and independent curved geometry order.
- DC background-field dependencies and invalidation; harmonic EM, mechanics, coupled studies and frequency sweeps.
- Mechanical modal ROM eligibility, eigensolvers, enrichment and limitations; damping and supported numerical settings.
- Validation, job execution, cancellation, failure and numerical convergence; saved runs and result reopening.
- Renderer fallback behavior and its limitations.

Guidance distinguishes controls actually exposed through the GUI from solver/API capabilities. It records that 3D coupled ROM reduces the mechanical block while EM/DC remain full order; EM, transient and persistent/offline ROM are not documented as supported. Execution completion is separate from convergence and loading saved results. Small examples are identified as verification examples, not proof of production accuracy. Historical names and stable identifiers are retained where needed for compatibility or historical context.

## Implementation and package decisions

- The existing documentation builder remains the single build path. It copies notebook inputs to a temporary source tree, materializes Windows notebook-link placeholders, and builds saved outputs without executing numerical notebooks.
- The packaged build supplies the app version to Sphinx. MyST substitution now renders that version in the landing-page body. The title is `LORENTZ — 0.2.8.dev332 Engineering Documentation`, without a duplicate brand. This also fixes a defect found in the packaged UI review: the previous landing page showed a literal release placeholder.
- MathJax New Computer Modern font assets are bundled from the configured `mathjax-newcm-font/chtml` location. Verification checks the browser's loaded local fonts rather than relying on Resource Timing, which did not list successful `file://` font requests.
- The native package manifest now excludes only the temporary `.runtime-copy-complete` staging marker and Python-generated `.pyc`/`__pycache__` files in addition to the manifest itself. These files are absent or are created dynamically after first launch. The manifest still hashes the executable, application sources, docs, lockfile, Python runtime, DLLs and other shipped files.
- The existing Help integration already locates the packaged site using `MMFEM_DOCUMENTATION_DIR`. If no local site is found, the application displays an actionable warning. This missing-site branch was verified with a focused call-level check; the real packaged build always contains docs.
- GUI application source was unchanged during G1: the GUI diff from accepted dev330 commit `f60b2a9` to the packaged source commit `b1c82d6` contains only the living roadmap. The build reused the accepted dev330 static frontend bundle; the source comparison confirms no intervening GUI changes, and the new full package manifest hashes the actual frontend assets. The Python host and documentation are rebuilt from the committed native repo source.

No new application feature or numerical code was added. The only G1 closeout code change is in the native package manifest contract and its focused builder test. Earlier G1 docs and test changes are in the native history beginning at `3729a781e7e436854122627aabb8c792f7061419`.
